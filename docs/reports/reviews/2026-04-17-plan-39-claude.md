## Findings

### MAJOR (blocking — must revise before approval)

- **`StockDataSource.fetch()` signature mismatch in plan pseudocode.** Plan line 100: `df = self._source.fetch(ticker)`. Actual signature in `signals/data_sources.py:78-84` is `fetch(self, ticker, start_date, end_date, use_cache=True)` with `start_date` and `end_date` **required**. The plan openly hedges this in §Pseudocode bullet 2 ("verify exact method name against `signals/data_sources.py` at implementation time") and §Risks bullet 3 ("API drift… 1-line correction, not a scope change"). This is not a 1-line correction: the orchestrator must source a date range from somewhere (config? CLI args? hard-coded lookback like "last 90 days"?), and that decision shapes the test matrix (e.g., `test_watchlist_runner_per_ticker_pipeline` needs to assert on the exact dates passed). **The plan's silence on date-range sourcing means the pseudocode is unimplementable as written and the TDD test list does not cover a real design decision.** Fix: decide date-range policy (e.g., "90 trading days ending today", or a new `lookback_days` config knob), update pseudocode, and add a test for it.

- **Acceptance-criteria drift from the issue body.** Issue #39 explicitly says "Each consumer accepts `market_hours_aware` / `intraday_ttl_minutes` (default False / 15) and threads them into `StockDataSource`." The plan replaces this with a new orchestrator class in a new module, and touches `alert_engine.py`, `trend_detector.py`, `dashboard.py` ZERO times. The plan's §Risks bullet 1 acknowledges the redirect and asks the user to confirm at approval time — but the Acceptance Criteria section does NOT include a line like "Issue #39 redirect from three-module edit to orchestrator is explicitly approved by issue owner." Without that, a reviewer checking the issue body against the plan will reasonably flag this as "plan does not implement the issue." The redirect may well be correct (see `docs/reports/2026-04-16-realtime-phase1-design.md` §7 listing the three consumers as deferred follow-ups), but the plan must (a) escalate the scope-change decision to the issue and (b) add an explicit acceptance criterion that the redirect is approved, not just the code changes.

- **`test_watchlist_runner_default_does_not_import_market_hours` tests the wrong thing.** The plan's own pseudocode imports `market_hours` ONLY inside `main()`'s `if args.intraday:` branch — `WatchlistRunner` itself never imports it. Monkeypatching `sys.modules["assethold.utils.market_hours"] = None` then instantiating `WatchlistRunner(Watchlist())` with `market_hours_aware=False` and calling `.run()` will of course not raise — because nothing in the code path touches the module whether or not the flag is on. The test provides zero signal about the actual lazy-import invariant. The real invariant to test is: *"default construction of `StockDataSource(market_hours_aware=False)` followed by `._is_cache_valid()` does not import `pandas_market_calendars`."* That test belongs on `StockDataSource` and is already implicit in Phase 1's `test_data_sources_market_hours.py`. The proposed test is an empty assertion dressed up as lazy-import coverage.

- **`--intraday` / `--no-intraday` CLI contract is unspecified and conflicts with config.** Plan line 126: `market_hours_aware=args.intraday or config.get("market_hours_aware", False)`. With `action="store_true"`, `args.intraday` is `False` when the flag is absent, so `config.market_hours_aware: true` wins — matches the plan's prose. **But if the user wants to override config and force `False`, there is no way to do it** (no `--no-intraday`, and a store_true flag cannot express "explicitly off"). The plan's §Open Questions never raises this; the test `test_watchlist_runner_cli_intraday_reads_config_when_flag_absent` codifies the partial behavior without flagging the missing override path. The daily_strategy CLI has the same issue (no `--no-intraday`), but because its config knob lives under `scoring:` and not as a top-level toggle, the ambiguity never surfaces there. Fix: either add `--no-intraday` (argparse `BooleanOptionalAction`) or explicitly document "config is the authoritative default; `--intraday` can only raise, never lower, the setting" and add a test asserting that contract.

### MINOR (non-blocking — address before or during implementation)

- **`insider_flags=[]` hard-coded produces silently incomplete alerts.** Plan line 105: `alerts = self._engine.build_alerts(ticker, trend_events, insider_flags=[])`. Reading `alert_engine.py:192-215`, missing insider flags means the CRITICAL-severity `unusual_insider_activity` alerts simply never fire — they don't raise, they don't warn, they just don't exist. The orchestrator's output dict will look correct but misleading to any downstream operator expecting the full alert set. The plan's §Open Questions bullet 2 flags the deferral but should (a) log a WARNING on first run that insider feed is disabled and (b) add a named CLI flag like `--with-insider-feed` (off by default) so the future wiring has a landing spot. Without this, a future reader will silently inherit the empty list as if it were intentional complete data.

- **Top-level YAML placement of `market_hours_aware` / `intraday_ttl_minutes` is inconsistent with existing file shape.** `config/stocks/watchlist.yml` already has a `settings:` block (lines 85–89) containing `cache_ttl_hours: 24` and `rate_limit_seconds: 2.0`. The new knobs are semantic siblings of `cache_ttl_hours`. Placing them at the top level (plan §Files to Change) splits related cache knobs across two locations. Fix: put them under `settings:` and update the pseudocode's `config.get(...)` calls to read from `settings`. This also removes any risk that a future `Watchlist` schema validator (currently none) would treat the new keys as unknown.

- **`render_charts=True` is on the critical path but untested end-to-end.** Plan line 107–109 calls `dashboard.build_price_chart(df, ticker)` then `dashboard.save_chart(fig, self._charts_output_dir / f"{ticker}.html")`. If `charts_output_dir` is `None` (as when `--charts-dir` is omitted but `--render-charts` is passed), the `/` operator on `None` raises `TypeError`. No test in the list exercises the `render_charts=True` path; `test_watchlist_runner_render_charts_off_by_default` only covers the OFF case. Add at least one test for `render_charts=True` with a tmp_path dir, and guard the `None` case in the orchestrator (either require `charts_output_dir` when `render_charts=True` or default to a sane location).

- **`load_watchlist_config` and `print_summary` do not exist.** Plan lines 115 and 132 invoke both as if they were imported helpers. Grep confirms no such functions in the repo (the only `print_summary` is `reporter.print_summary` in `daily_strategy/report.py`). The plan must either list these as new private helpers in the Files-to-Change table with their intended signatures, or reference existing equivalents. As written, a reader cannot tell whether they're new code, reused code, or placeholders.

- **Acceptance criterion "Default runs without importing `pandas_market_calendars`" lacks a stated verification method that actually works.** Plan line 182: *"verified via `PYTHONPATH='' python -c "import sys; ..."` style check or equivalent monkeypatch test."* `PYTHONPATH=''` does not help — it just strips extra search paths; Python still resolves site-packages. The correct verification is a subprocess invocation that imports the module and then asserts `"pandas_market_calendars" not in sys.modules`. Phase 1's Acceptance Criterion #5 (design doc line 236) has the same claim and it was verified by a focused test, not a subprocess. Pick one and state it precisely.

- **Complexity T2 sizing is optimistic if the date-range decision (MAJOR #1) expands scope.** Plan estimates ~150 LOC + 8 tests + integration test + config edits. If `lookback_days` becomes a config knob, add ~20 LOC and 2 tests for that. If `insider_flags` gets its own flag (MINOR #1), add ~30 LOC and 2 more tests. If `--no-intraday` is added (MAJOR #4), add ~10 LOC and 1 test. T2 is still defensible but tight; T2-upper. Flag for revisit if any of the above bullets expand scope.

- **Orchestrator re-constructs `StockDataSource` inside `run()` (line 94–97) rather than in `__init__`.** The docstring on line 82 claims this is intentional ("Lazy-constructed; do not touch pandas_market_calendars here"). But `StockDataSource.__init__` itself is cheap and does NOT import `pandas_market_calendars` (the import is inside `_is_cache_valid`). The lazy-source pattern adds a field (`self._source = None`) that must then be null-checked anywhere else it's read, and makes `run()` non-idempotent in the sense that calling `.run()` twice creates two sources. Simpler design: construct the source in `__init__` and drop the `None`. The lazy-import discipline is already guaranteed by `data_sources.py` itself.

- **`test_watchlist_runner_market_hours_aware_true_wires_data_source` stubs `StockDataSource` as a spy.** This risks sliding into a "testing the mock" anti-pattern (explicitly forbidden by `.claude/CLAUDE.md` Part 1: "YOU MUST NEVER write tests that 'test' mocked behavior"). Better: construct a real `StockDataSource(market_hours_aware=True, intraday_ttl_minutes=15)` and assert `.market_hours_aware is True` and `.intraday_ttl == timedelta(minutes=15)` on the instance the runner holds. That test touches zero I/O and tests real wiring.

- **The `settings.cache_ttl_hours` existing knob is silently orphaned by the plan.** `watchlist.yml:87` already declares `cache_ttl_hours: 24`, but `Watchlist` never reads `settings` — only `stocks`. The plan adds two more toggles into the same orphan zone. Fix (optional in this issue, required eventually): either wire `settings.cache_ttl_hours` through to `StockDataSource(cache_ttl_hours=...)` and treat this issue as the moment to close that gap, or file a follow-up and state explicitly that `settings` is read-your-own-risk config.

## Final verdict

MAJOR

Rationale: The `fetch(ticker)` pseudocode is unimplementable — it will raise `TypeError` at runtime because `start_date`/`end_date` are required — and the plan's hedge ("1-line correction") understates a real design decision about date-range sourcing that must be made before implementation. The lazy-import regression test monkeypatches a module that the code under test never imports, which is a false-confidence test. The issue body asks for edits to three existing modules and the plan delivers a new module instead, without surfacing that redirect into the Acceptance Criteria. And the `--intraday` / config interaction has no way to express "config says true, I want false right now." These are correctness-critical defects that must be resolved before approval; none are cosmetic. Revise and re-submit.
