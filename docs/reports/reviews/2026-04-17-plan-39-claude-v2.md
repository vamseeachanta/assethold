- **(d) `--no-intraday` override: FIXED.** `argparse.BooleanOptionalAction` (pseudocode line 187) is Python 3.9+ available and `pyproject.toml` requires `>=3.9`. With `default=None`, absence of the flag yields `args.intraday = None`; `--intraday` yields `True`; `--no-intraday` yields `False`. Precedence at pseudocode lines 204–207 correctly uses `is not None` check before falling back to config. If a user passes BOTH `--intraday --no-intraday`, argparse processes them left-to-right and the last one wins (standard `BooleanOptionalAction` behavior), so `--intraday --no-intraday` → `False`, `--no-intraday --intraday` → `True`. The plan does not document the "last wins" semantic but it is the standard argparse contract, so this is acceptable. Tests `test_cli_no_intraday_overrides_config_true` and `test_cli_no_flag_falls_back_to_config` encode the core cases. `test_cli_intraday_wins_over_no_intraday_when_both_passed` would strengthen coverage but is MINOR.

### MINOR (non-blocking)

- **Internal inconsistency: `Watchlist.get_settings()` helper is promised but not used.** Decision #7 commits to adding `get_settings() -> dict` as a narrow helper, Files-to-Change table lists `src/assethold/signals/watchlist.py (add ~10 LOC method)`, and §Complexity budgets "~10 LOC `Watchlist.get_settings()` helper." **But the pseudocode `main()` at line 201 uses `config.get("settings", {})` directly** — `config` is the dict returned from `watchlist.load()`, so the helper is bypassed. Either (a) `main()` must call `watchlist.get_settings()` for the helper to have a caller, or (b) the helper is unnecessary dead code and Decision #7 should drop it. Risk if left as-is: implementation ships the helper untested from the CLI path and the "narrow getter instead of mutating existing methods" claim in Decision #7 becomes hollow. The `get_settings()` helper *does* still get exercised by `Watchlist.get_settings()`-specific tests mentioned in §Implementation Sequencing step 7, so this is code cleanliness, not a functional break — hence MINOR. Pick one of (a)/(b) and stick with it.

- **`date.today()` monkeypatching is non-trivial and the plan is silent on how.** `datetime.date.today` is a C-implemented classmethod on the built-in `date` class and cannot be monkeypatched via `monkeypatch.setattr(date, "today", ...)` — it raises `TypeError: cannot set 'today' attribute of immutable type 'datetime.date'`. Standard workarounds: (1) patch the *module-level name* `watchlist_runner.date` to a subclass with overridden `today()`; (2) use `freezegun` (not in `dev` deps of `pyproject.toml`); (3) restructure `_date_range()` to accept an injected `today: date | None = None` parameter. The plan's test table row for `test_date_range_uses_today_minus_lookback_days` says "monkeypatched `date.today` to fixed 2026-04-17" without picking an approach. Implementation will discover this friction. Recommend adding to Decision #1: "Test monkeypatches the module-level `date` binding (`monkeypatch.setattr('assethold.signals.watchlist_runner.date', FrozenDate)`) since `date.today` is C-level immutable." This is an implementation-detail gap, not a correctness defect — MINOR.

- **Lazy-import invariant test has a `sys.modules` cross-contamination risk the plan hedges but does not resolve.** Test `test_default_construction_does_not_import_pandas_market_calendars` asserts `"pandas_market_calendars" not in sys.modules` post-construction. If any earlier test in the pytest session imported it (e.g., Phase 1's `test_data_sources_market_hours.py` which explicitly exercises `market_hours_aware=True`), the assertion fires a false positive. Pytest module cache + `sys.modules` is global per-process. The plan says "fresh subprocess or careful `sys.modules` snapshot around construction" in the TDD table but does not commit to subprocess. Spot-checked approach: `subprocess.run([sys.executable, "-c", "from assethold.signals.watchlist_runner import WatchlistRunner; ..."])` and assert on exit. This needs to be the committed approach; a "snapshot" in-process approach is fragile. Elevate to Decision #8 clarification.

- **`test_init_warns_when_insider_provider_missing` relies on pytest's `caplog` default level.** Pytest's `caplog` captures WARNING by default at the root logger, but only if the target logger's level permits propagation. `logging.getLogger(__name__)` in a fresh module with no explicit `setLevel` inherits from root (usually WARNING), so the test *should* work. However, if another conftest configures `assethold.signals.watchlist_runner` logger to a higher level, the test silently fails to capture. Standard defensive pattern: test sets `caplog.set_level(logging.WARNING, logger="assethold.signals.watchlist_runner")` explicitly. Plan does not specify this. MINOR — implementation-time discipline.

- **"Once per run" framing for the insider warning is ambiguous.** Decision #4 says "logs a WARNING once per run (not per ticker)." But the warning fires in `__init__` (pseudocode line 145), which is once *per instance*, not per run. If a future scheduler or retry-loop instantiates `WatchlistRunner` multiple times per run, the warning fires N times. Current `main()` constructs exactly one instance per invocation, so the framing holds for today's caller — but the Decision text should be precise: "WARNING fires once per `WatchlistRunner.__init__`; current CLI creates one runner per invocation, so this is once per run in the current flow." This guards future maintainers against assuming a per-run deduplication exists. MINOR.

- **Acceptance Criteria item "Three adversarial reviews… Gemini is optional if capacity-exhausted" doesn't specify where the "document fallback" lands.** The bullet says Gemini may be skipped if capacity-exhausted "(document fallback)" but does not say where (this review file? the plan's Adversarial Review Summary? a comment on #39?). The rule-of-three policy from the skill requires explicit recording of provider-failure substitution. Plan should say: "If Gemini returns 429, add a row to §Adversarial Review Summary v2 table citing the failure and proceed with Claude+Codex." MINOR.

- **`_print_summary(results)` uses `sorted(results.items())` which sorts by ticker alphabetically, but plan text doesn't specify the summary output contract.** Not wrong, but if a future test asserts a specific order (e.g. insertion order matching watchlist YAML order), sorted(items()) will fail that test. Recommend either (a) documenting "summary order is alphabetical by ticker" in pseudocode comment, or (b) using `results.items()` to preserve insertion order (matches watchlist order, slightly more useful for operators scanning a small output). MINOR — cosmetic.

- **`main()` passing `argv=None` to `_build_arg_parser().parse_args(None)` is correct, but the docstring/help should note that `main()` is callable as a Python function (not just via `__main__`).** Behavior: `parse_args(None)` falls through to `sys.argv[1:]`; `parse_args([])` parses empty argv; `parse_args(["--intraday"])` parses that list. All three correct. MINOR documentation nit.
